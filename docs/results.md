# 結果と限界

数値はすべて `results/` に保存したJSONから読み取ったものです。BPCは1文字あたりのビット数で、小さいほど良い値です。特記がない限り単一seedの1回の実行で、評価方式が版ごとに異なるため、表をまたいだ数値の直接比較はできません。

GPUピークは5,256 MiBでした。ノードは増えていますが、BPCはほぼ横ばいです。

## 外部記憶（v2.0〜v2.1）

出典：[results_v20_engram.json](../results/results_v20_engram.json)、[results_v20b_calibrated.json](../results/results_v20b_calibrated.json)、[results_v21_thought_engram.json](../results/results_v21_thought_engram.json)。

- **着脱。** 架空の設定文のBPCは、装着前5.924、装着中3.401、取り外し後5.924でした。
- **収録量。** Wikipedia記憶を5,000万、1億、1億5,000万、2億文字と増やすと、WikipediaのBPCは4.6934、4.6831、4.6701、4.6602になりました（本体のみは4.7523）。
- **ゲート。** 3つの記憶を同時に使うと、文脈ゲートと不確実性ゲートで3分野とも本体のみより改善しましたが、全分野で最良の設定はありませんでした。
- **文章記憶。** 検索によるBPCは3分野とも下がりましたが、話題の維持を測る指標は改善しませんでした。正しい記憶を検索できても、生成では固有名詞が「アストラインカ」のように崩れました。

## Transformerとの参考比較

出典：[results_transformer_baseline.json](../results/results_transformer_baseline.json)、[results_v14_90m_6sys.json](../results/results_v14_90m_6sys.json)。

| 項目 | Transformer | ENNE v1.4 |
|---|---|---|
| 学習データ | やさしい日本語のみ（ランダムに切り出して反復） | やさしい日本語・青空文庫・Wikipediaの3分野を混合した新しい文章 |
| 入力 | 4,096文字の語彙。出現5回未満の文字は`<UNK>` | UTF-8の全バイト。`<UNK>`なし |
| 学習 | 誤差逆伝播＋AdamW、587万パラメータ | 局所更新、約314万ノード＋長期記憶 |
| 時間 | 300.8秒で延べ5,400万文字 | 1ラウンド約850秒で1,500万文字。評価・枝刈り・統合の時間を含む |
| GPUピーク | 2,250 MiB | 5,256 MiB |
| やさしい日本語306k評価のBPC | 3.8001 | 4.2588 |

予測損失ではTransformerが低い値を出しています。ただしTransformerは評価と同じ分野だけを学習しており、まれな文字を`<UNK>`にまとめて評価しているため、Transformerに有利な条件です。学習時間も、データ・計時範囲・処理する文字の種類が違うため、どちらが安いとは判断できません。公平に比べるには、同じ3分野のデータ、バイト単位でUNKのないTransformer、純粋な学習時間、同じ評価器をそろえる必要があります。

## まとめ：言えること・言えないこと

**言えること**
- 本体・記憶・索引・対話・ゲート・仲裁を部品ごとに学習し、他の部品を再学習せずに追加できた。部品の学習・構築は数ミリ秒から数分で、記憶・索引・ゲート・仲裁はCPUだけで学習できた
- 本体単独のBPCは小さなTransformerより悪いが、部品を組み合わせると、根拠のある回答、後から足した知識への回答、未知の問いへの棄権、短い挨拶への応答ができた
- 誤差逆伝播なしの局所更新で、ノードを増減させながら日本語のバイト列を予測するモデルを、12GBのGPUで数百万ノード規模まで動かせた
- 本体と知識を分け、記憶の着脱で予測への影響を足し引きできた
- 冒頭文検索と棄権を組み合わせると、小規模な既知問題では根拠のある回答と「情報がありません」を出し分けられた

**言えないこと**
- Transformerを上回った、推論能力を獲得した
- 学習コストや予測性能でTransformerに対して優劣がある（公平な比較は未実施）
- 規模を大きくすれば本体が良くなる
- 成長型仲裁層が単純なゲートより優れている
- 本体に学習した知識を完全に消せる

## 次の検証

1. コード・モデル・索引・設定・評価器を新しいIDで固定する
2. 未見の問題を確定してから一度だけ評価する
3. 単一ゲート・合議・仲裁を同じ入力で比べ、成長機構や索引改善の寄与を切り分ける
4. 正答、根拠との整合、比較説明、語用、適切な棄権、過剰な棄権を分けて評価し、人手評価を併記する
5. 同じ3分野データ・バイト単位・同じ評価器・純粋な学習時間で、Transformerや検索拡張モデルと比較する
